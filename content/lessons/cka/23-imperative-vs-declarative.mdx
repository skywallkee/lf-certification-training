## Why there are two styles

Every change you make to a cluster ends up as a request to the API server. What differs is how much of the thinking
you do yourself.

Think of a taxi. You can give **directions**: turn left, go straight for two streets, stop here. That works, but only
if you know exactly where the car is right now, and afterwards nobody can tell where you meant to go. Or you can give
the **address**. The driver works out the route from wherever the car happens to be, and you can hand the same address
to any driver on any day.

- **Imperative** is the directions. You tell Kubernetes which operation to perform: *create* this, *scale* that,
  *delete* this. You are responsible for knowing the current state and for choosing the right next step.
- **Declarative** is the address. You write down what should exist, in a file, and `kubectl apply` compares it with
  the cluster and performs whatever operations are needed: create, change or nothing at all.

<KeyIdea>
Imperative: you say **what to do**. Declarative: you say **what you want**, and the tool works out what to do. The
exam rewards being fluent in both: commands for speed, files for anything you must get exactly right or change later.
</KeyIdea>

## What the two styles are

<Diagram id="two-styles" />

The Kubernetes documentation splits this into **three techniques**, and the middle one is the one that confuses
people:

| Technique | Typical commands | You keep | Who chooses the operation |
|-----------|------------------|----------|---------------------------|
| Imperative commands | `kubectl run`, `create deployment`, `expose`, `scale`, `set image`, `edit`, `label`, `delete` | Nothing: the cluster is the only record | You |
| Imperative object configuration | `kubectl create -f`, `replace -f`, `delete -f` | A file per object | You |
| Declarative object configuration | `kubectl apply -f`, `kubectl diff -f` | Files or whole directories | kubectl, per object |

Notice that **a YAML file does not make you declarative; the verb does**. `kubectl create -f web.yaml` is still an
order ("create this"), and it fails if `web` already exists. `kubectl apply -f web.yaml` is a statement ("this should
exist, like this"), and it succeeds whether `web` is missing, outdated or already correct.

That last property has a name: **idempotent**. Running the same `apply` twice gives the same result as running it
once, which is what makes it safe in scripts, pipelines and GitOps tools.

```bash
kubectl create -f web.yaml     # second run: Error from server (AlreadyExists)
kubectl apply  -f web.yaml     # second run: deployment.apps/web unchanged
```

## How it works underneath

### Kubernetes itself is always declarative

<Diagram id="reconcile" />

Here is the part the comparison tables leave out. The choice between imperative and declarative is only about **how
you talk to the API server**. Inside the cluster there is only one model: every object has a `spec` (what you want)
and a `status` (what exists), and controllers work in a loop to make the second match the first.

`kubectl scale deployment web --replicas=5` does not start two Pods. It changes one number, `spec.replicas`, and
returns. The Deployment controller, the ReplicaSet controller, the scheduler and the kubelet then notice the gap and
close it. That is also why Kubernetes heals itself: if a Pod dies, nobody has to give a new order, because the desired
state still says five.

So an imperative command is a quick way to **edit desired state**. A declarative file is a way to **own desired
state**: keep it, review it, version it and apply it again.

<DeepDive title="What each kubectl verb sends to the API server">
| You type | kubectl sends | If the object exists | If it does not exist |
|----------|---------------|----------------------|----------------------|
| `kubectl create ...` or `create -f` | `POST` (create) | Fails: AlreadyExists | Creates it |
| `kubectl replace -f` | `PUT` (update the whole object) | Overwrites it with the file | Fails: NotFound |
| `kubectl apply -f` | `GET`, then `PATCH` or `POST` | Patches only what differs | Creates it |
| `kubectl scale`, `set image`, `label`, `edit` | A change to a few fields | Changes those fields | Fails: NotFound |
| `kubectl delete` | `DELETE` | Deletes it | Fails: NotFound (unless `--ignore-not-found`) |

`replace` and `apply` look similar and are not. `replace` sends the **whole object** as it is in your file, so
anything that is in the live object but not in the file is dropped, including changes made by other people or tools.
`apply` sends a **patch**, so everything it does not mention survives.
</DeepDive>

### How `kubectl apply` decides what to change

<Diagram id="apply-merge" />

To be able to send only the difference, `kubectl apply` needs to know what you asked for last time. It stores a copy
of your file on the object itself, in the annotation `kubectl.kubernetes.io/last-applied-configuration`. On every run
it compares three things:

1. **Your file**: what you want now.
2. **The last-applied annotation**: what you asked for last time.
3. **The live object**: what the cluster has, including defaults and fields set by controllers.

From them it works out a patch with two simple rules:

- **Set** every field in the file whose value differs from the live object.
- **Clear** every field that is in last-applied but no longer in the file: you removed it, so it should go.

Anything else is left alone. A field that is only in the live object (a default, a `status`, an annotation added by a
controller, a replica count managed by an autoscaler) was never yours, so `apply` does not touch it.

You can read the stored copy at any time:

```bash
kubectl apply view-last-applied deployment/web
```

<DeepDive title="Server-side apply: the same idea, tracked per field">
The annotation approach is called **client-side apply**, because kubectl does the comparison. Its weakness is that it
only remembers what *kubectl apply* did. It does not know that someone else scaled the Deployment, so it can silently
overwrite their change.

**Server-side apply** (`kubectl apply --server-side`) moves the merge into the API server. Instead of one annotation,
the server records an owner for every field in `metadata.managedFields`: each writer is a **field manager**. If you
apply a different value for a field that another manager owns, you get a **conflict** error instead of a silent
overwrite. You then decide: change your file to match, drop the field from your file, or take the field over with
`--force-conflicts`.

```bash
kubectl apply --server-side -f web.yaml
kubectl get deployment web --show-managed-fields -o yaml   # who owns which field
```

Client-side apply is still kubectl's default and is all you need for the exam, but controllers and GitOps tools
increasingly use server-side apply.
</DeepDive>

## When to use which

| | Imperative commands | Imperative with files | Declarative (`apply`) |
|---|---|---|---|
| Speed for a single small change | Fastest | Slow | Medium |
| Record of what you intended | None | The file | The file |
| Review and version control | No | Yes | Yes |
| Safe to run again | No (create fails) | No | Yes |
| Keeps changes made by others | Yes (touches few fields) | **No**: `replace` overwrites | Yes |
| Works on a whole directory | No | One verb for all files | Yes, mixed create and update |
| Every field available | No, only what flags offer | Yes | Yes |
| Best for | Exam tasks, experiments, quick fixes | Recreating an object from a saved file | Real clusters, teams, automation |

In production the answer is almost always declarative: files in Git, applied by a pipeline. In the exam the answer is
"whatever is fastest and correct", which usually means imperative commands for simple objects and generated YAML for
the rest.

<Callout kind="warning" title="Pick one style per object">
The styles do not mix well on the same object. A change made with `kubectl scale` or `kubectl edit` lives only in the
cluster. If the file also sets that field, the next `kubectl apply` puts the file's value back without any warning.
</Callout>

## Using it

<Example title="Imperative: create, change and expose a Deployment in four commands">
Run `nginx` with three replicas, scale it, roll out a newer image and make it reachable inside the cluster.

```bash
kubectl create deployment web --image=nginx:1.28 --replicas=3
kubectl scale deployment web --replicas=5
kubectl set image deployment/web nginx=nginx:1.29     # container name = image name by default
kubectl expose deployment web --port=80
```

Fast, and nothing to clean up. But nothing records what you did either: to rebuild `web` on another cluster you would
have to remember all four commands, in order.
</Example>

<Example title="Declarative: the same Deployment as a file">
Describe the result once:

```yaml
# web.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.28
```

```bash
kubectl apply -f web.yaml          # deployment.apps/web created
kubectl apply -f web.yaml          # deployment.apps/web unchanged
```

To change it, **edit the file**, look at what would change, then apply:

```bash
sed -i 's/nginx:1.28/nginx:1.29/' web.yaml
kubectl diff -f web.yaml           # shows the image line with - and +
kubectl apply -f web.yaml          # deployment.apps/web configured
```

`apply` takes a directory too: `kubectl apply -f manifests/` creates what is missing and updates what changed, and
`-R` goes into sub-directories.
</Example>

<Example title="The exam hybrid: let a command write the file">
Task: a Deployment `api` with two replicas of `nginx:1.29`, where each container requests 100m of CPU. No imperative
flag sets resource requests on `create deployment`, so generate the manifest and add them.

```bash
kubectl create deployment api --image=nginx:1.29 --replicas=2 --dry-run=client -o yaml > api.yaml
```

`--dry-run=client` builds the object without sending it, and `-o yaml` prints it. Open `api.yaml`, find the empty
`resources: {}` and fill it in:

```yaml
        resources:
          requests:
            cpu: 100m
```

```bash
kubectl apply -f api.yaml
kubectl get deployment api -o jsonpath='{.spec.template.spec.containers[0].resources}'
```

You typed four lines of YAML instead of twenty, and the selector and labels cannot be wrong.
</Example>

<Example title="Change something that cannot be changed in place">
Most fields of a running Pod are immutable. If a task asks you to change one (a command, a volume, an environment
variable), neither `edit` nor `apply` can do it. Save the Pod, fix the file, and replace it:

```bash
kubectl get pod worker -o yaml > worker.yaml
vim worker.yaml                              # make the change
kubectl replace --force -f worker.yaml       # deletes the Pod, then creates it from the file
```

`replace --force` is imperative on purpose: it says "delete and create", which is exactly what an immutable field
needs. For Pods owned by a Deployment, change the Deployment instead and let it roll out new Pods.
</Example>

## Tricks

<Trick title="Know which objects have a generator">
`kubectl create` can write these for you: `deployment`, `service`, `configmap`, `secret`, `namespace`,
`serviceaccount`, `role`, `rolebinding`, `clusterrole`, `clusterrolebinding`, `job`, `cronjob`, `ingress`, `quota`,
`priorityclass` and `poddisruptionbudget`. `kubectl run` makes a Pod, `kubectl expose` a Service and
`kubectl autoscale` a HorizontalPodAutoscaler. For kinds with no generator (PersistentVolume, PersistentVolumeClaim,
NetworkPolicy, StorageClass, DaemonSet, StatefulSet) copy an example from the documentation, which you may open
during the exam.
</Trick>

<Trick title="Save the typing with a variable">
Set this once at the start of the exam and every generator command gets shorter:

```bash
export do="--dry-run=client -o yaml"
kubectl run tmp --image=busybox:1.37 $do -- sleep 3600 > tmp.yaml
```
</Trick>

<Trick title="When kubectl edit refuses, use the copy it saved">
If you change an immutable field in `kubectl edit`, kubectl rejects the change but tells you it stored your version,
with a line such as `A copy of your changes has been stored to "/tmp/kubectl-edit-1234.yaml"`. Do not start over:

```bash
kubectl replace --force -f /tmp/kubectl-edit-1234.yaml
```
</Trick>

<Trick title="Preview before you apply">
`kubectl diff -f web.yaml` shows exactly what `apply` would change on the live object, without changing anything.
`kubectl apply --dry-run=server -f web.yaml` goes one step further: the API server validates the object and runs
admission, but does not store it. Use it to catch a typo in a field name before it costs you a task.
</Trick>

<Trick title="Imperative edits are fine when no file exists">
If an object was created imperatively and no manifest is kept, `kubectl edit`, `scale` and `set image` are the right
tools: there is no file to fall out of date. The trap only exists once a file claims to be the truth.
</Trick>

## Common mistakes

- **Running `kubectl create` twice.** The second run fails with `AlreadyExists`. If you are fixing a file and trying
  again, use `kubectl apply -f`, or `kubectl replace --force -f` when the fix touches an immutable field.
- **Editing the cluster, then applying the old file.** `kubectl edit` and `kubectl scale` do not update your YAML.
  The next `apply` reverts every field the file names. Change the file first, then apply.
- **Using `replace` where `apply` was meant.** `replace` overwrites the whole object from the file and fails if the
  object is missing. It also drops fields that others set, such as replicas managed by an autoscaler.
- **`apply` on an object made with `create`.** It works, but kubectl warns that the last-applied annotation is
  missing and adds it. From then on removing a field from the file clears it; fields removed before that point stay.
  To avoid the warning, create with `kubectl create --save-config` or simply use `apply` from the start.
- **Expecting a deleted file to delete the object.** `apply` only looks at the files you give it. Removing
  `web.yaml` from a directory leaves `web` running: delete it with `kubectl delete -f web.yaml` before removing the
  file, or `kubectl delete deployment web` after.
- **Setting `replicas` in a file when an autoscaler owns it.** Every `apply` resets the count. Leave `replicas` out
  of the manifest and `apply` will keep whatever the autoscaler chose.

## Recap

- **Imperative** = you give the steps (`run`, `create`, `scale`, `set`, `edit`). **Declarative** = you describe the
  result in a file and `kubectl apply` works out the steps.
- A file is not enough: `create -f` and `replace -f` are still imperative. Only `apply` is declarative.
- Inside the cluster everything is declarative: controllers move actual state toward `spec`, whatever you typed.
- `apply` compares your file, the last-applied annotation and the live object, and patches only the difference.
- In the exam: imperative for one-liners, `--dry-run=client -o yaml` plus `apply` for the rest, and never let a
  hand-made change and a file disagree.
