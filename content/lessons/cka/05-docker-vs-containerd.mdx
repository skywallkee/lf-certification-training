## Why this matters

Most people meet containers through Docker, so it is natural to assume that Kubernetes "runs Docker containers".
It used to. Today a typical node has **no Docker on it at all**, and the `docker` command you may reach for when
something breaks is simply not there.

That raises three questions, and this lesson answers each of them:

1. If Docker is gone, what runs the containers?
2. Why did the images you built with Docker keep working?
3. What do you type on a node instead of `docker ps`?

<KeyIdea>
Docker is a toolbox for people; containerd is the engine inside it. Kubernetes only ever needed the engine, so it
now talks to containerd directly, through a standard interface called CRI.
</KeyIdea>

## What Docker really is

<Diagram id="docker-inside" />

"Docker" is not one program. It is a stack, and each layer has a different job:

| Layer | What it does | Does Kubernetes need it? |
|-------|--------------|--------------------------|
| `docker` CLI | Commands for people: `build`, `run`, `push`, `compose` | No. Kubernetes has its own API and `kubectl` |
| `dockerd` (the Docker daemon) | REST API, image builds, volumes, networks, registry logins | No. Kubernetes has volumes, CNI and image pull secrets of its own |
| **containerd** | Pulls and stores images, creates and supervises containers | **Yes** |
| **runc** | Starts one container: sets up namespaces and cgroups, then runs the process | **Yes** |

containerd was written by Docker as the core of Docker Engine, then split out and donated to the CNCF in 2017, where
it is now a graduated project. runc was donated even earlier, as the reference implementation of the Open Container
Initiative (OCI) runtime specification.

So when Kubernetes "dropped Docker", it did not swap one runtime for a rival. It stopped going through the top two
layers and kept talking to the bottom two, which had been doing the real work all along.

## How Kubernetes talks to a runtime

<Diagram id="before-after" />

### CRI, the plug

In the first Kubernetes releases, the kubelet contained code that called Docker directly. When other runtimes
appeared (rkt was the first), each one needed more special code inside the kubelet. That does not scale, so in
Kubernetes v1.5 (December 2016) the project defined the **Container Runtime Interface (CRI)**: a gRPC API, served
by the runtime on a Unix socket, with two services:

- **RuntimeService**: Pod sandboxes and containers (`RunPodSandbox`, `CreateContainer`, `StartContainer`,
  `StopContainer`, `ExecSync`, and so on).
- **ImageService**: images (`PullImage`, `ListImages`, `RemoveImage`).

Any runtime that serves those two services can run under the kubelet. The kubelet does not know or care what is
behind the socket.

### dockershim, the adapter that had to go

Docker predates CRI, and it never implemented it, because Docker is built for people and not for orchestrators. To
keep Docker working, the Kubernetes maintainers wrote an adapter, **dockershim**, and carried it *inside the
kubelet*. Every call went kubelet → dockershim → dockerd → containerd → runc.

That was a burden for two reasons: the Kubernetes project had to maintain code for one vendor's product, and new
runtime features (cgroups v2, user namespaces) had to be wired through Docker before Kubernetes could use them.
Dockershim was deprecated in v1.20 and **removed in v1.24** (May 2022). The next lesson, on the Docker
deprecation, covers what that meant for running clusters.

### OCI, the reason nothing broke

Two specifications from the Open Container Initiative make runtimes interchangeable:

- The **image specification** defines what an image is: a manifest, a config and a set of layer tarballs.
- The **runtime specification** defines how to start a container from an unpacked image.

`docker build` produces OCI images. containerd pulls and runs OCI images. That is the whole reason an image built
with Docker on a laptop runs on a containerd node without any change: there is no such thing as a "Docker image"
that only Docker can run.

<Callout kind="note" title="Three acronyms, three layers">
**CRI** is how the kubelet talks to a runtime. **OCI** is what an image and a container look like. **runc** is the
program that implements the OCI runtime specification. A question that mixes them up is usually testing whether you
know which layer each one belongs to.
</Callout>

## The runtimes you can choose

<Diagram id="cri-runtimes" />

| Runtime | What it is | Default CRI socket |
|---------|------------|--------------------|
| **containerd** | General-purpose runtime with a built-in CRI plugin. The usual choice for kubeadm, and what most managed clusters and k3s use | `unix:///run/containerd/containerd.sock` |
| **CRI-O** | A runtime built only for Kubernetes, released in step with it. Default in OpenShift | `unix:///var/run/crio/crio.sock` |
| **Docker Engine + cri-dockerd** | The dockershim code moved out of the kubelet into a separate adapter, for people who must keep Docker on their nodes | `unix:///run/cri-dockerd.sock` |

The kubelet finds its runtime through one setting, the **container runtime endpoint**. kubeadm detects the socket
when you run `kubeadm init` or `kubeadm join`; if a node has more than one runtime installed you must choose with
`--cri-socket`.

<Callout kind="warning" title="The runtime and the kubelet must agree on the cgroup driver">
On a systemd host, both the kubelet and the runtime should use the `systemd` cgroup driver. If containerd is left on
its own default (`cgroupfs`) while the kubelet uses `systemd`, Pods fail to start or the node becomes unstable under
load. In containerd's `/etc/containerd/config.toml` that is the `SystemdCgroup = true` option of the runc runtime.
Recent kubelets ask the runtime for its driver over CRI, but containerd itself still has to be set correctly.
</Callout>

## What happens on the node when a Pod starts

<Diagram id="pod-on-node" />

Walk through it once and `crictl` output will make sense forever:

1. The kubelet learns that a Pod was scheduled to its node and calls `RunPodSandbox`.
2. containerd starts a **shim** process for the Pod (`containerd-shim-runc-v2`). The shim is the parent of the
   Pod's containers and keeps their stdio and exit codes.
3. The shim uses runc to start the **pause container**. It does nothing; it exists to hold the Pod's network
   namespace, so the Pod keeps its IP while app containers restart. The CNI plugin then wires that namespace up.
4. The kubelet calls `PullImage` for each image the node does not have yet.
5. For each container in the Pod spec, the kubelet calls `CreateContainer` and `StartContainer`. runc starts the
   process inside the sandbox's namespaces, with the cgroup limits from the Pod spec.

This is why a Pod with one container shows up on the node as **one sandbox and one container**, and why
`crictl pods` and `crictl ps` are separate commands.

<DeepDive title="Details that explain odd behaviour">
- **Restarting containerd does not restart your Pods.** Containers are children of their shim, not of containerd.
  You can `systemctl restart containerd` after changing its config and running containers keep running.
- **containerd has its own namespaces**, which have nothing to do with Kubernetes namespaces. Everything the kubelet
  creates lives in the containerd namespace `k8s.io`; Docker Engine uses `moby`. That is why a bare `ctr containers
  ls` on a busy node prints nothing: it looks in the namespace `default`.
- **`docker build` on a node does not feed Kubernetes.** Even if Docker is installed next to containerd, an image
  built or pulled with Docker is stored for Docker, not in the `k8s.io` namespace the kubelet looks in. The Pod
  reports `ErrImagePull` unless you push the image to a registry or import it with
  `ctr -n k8s.io images import app.tar`.
- **Container logs are files.** The runtime writes each container's output to
  `/var/log/pods/<namespace>_<pod>_<uid>/<container>/<restart>.log`, and `kubectl logs` asks the kubelet to read
  that file. When the API server is down you can read the file directly.
- **The Docker socket is gone.** Anything that mounted `/var/run/docker.sock` from the host (old CI agents that ran
  `docker build` in a Pod, some monitoring agents) breaks on a containerd node. Build with a tool that needs no
  daemon, such as BuildKit or Kaniko.
</DeepDive>

## The command line tools

<Diagram id="cli-tools" />

| Tool | Comes from | Meant for | Talks to |
|------|------------|-----------|----------|
| `ctr` | containerd | Debugging containerd itself. Few features, unfriendly syntax | containerd's own API |
| `nerdctl` | containerd (separate install) | A general Docker replacement: same commands, plus build and compose | containerd's own API |
| `crictl` | Kubernetes (cri-tools) | **Debugging a Kubernetes node**. Works with every CRI runtime | The CRI socket |

`crictl` is the one to learn. It uses the same socket and the same API as the kubelet, so it shows Pods and
containers exactly as Kubernetes sees them, and it works the same on containerd and CRI-O.

Most of what you know from Docker carries over:

| Docker | crictl | Notes |
|--------|--------|-------|
| `docker ps -a` | `crictl ps -a` | Add `--name`, `--state` or `--pod` to filter |
| `docker images` | `crictl images` | |
| `docker pull` | `crictl pull` | |
| `docker rmi` | `crictl rmi` | `crictl rmi --prune` removes unused images |
| `docker logs` | `crictl logs` | Takes a container ID; `-f` and `--tail` work |
| `docker exec -it` | `crictl exec -it` | |
| `docker inspect` | `crictl inspect` | `crictl inspecti` for images, `crictl inspectp` for Pods |
| `docker stats` | `crictl stats` | |
| `docker info` | `crictl info` | Shows runtime status and config, including the cgroup driver |
| (no equivalent) | `crictl pods` | Lists Pod sandboxes; filter with `--name` and `--namespace` |
| `docker build`, `push`, `tag` | (no equivalent) | crictl is a debugging tool, not a build tool |

<Callout kind="warning" title="crictl is for looking, not for fixing">
The kubelet owns everything on the node. If you `crictl stop` or `crictl rm` a container that belongs to a Pod, the
kubelet notices and starts it again. And a Pod you create by hand with `crictl runp` is one the kubelet knows nothing
about, so it will be removed. Change Pods through the API (or the static Pod manifest), and use crictl to see what
happened.
</Callout>

## Using it

<Example title="Find out which runtime a cluster uses">
From anywhere with `kubectl`, the last column of the wide node list names the runtime and its version:

```bash
kubectl get nodes -o wide
```

```text
NAME   STATUS   ROLES           VERSION   ...   CONTAINER-RUNTIME
cp1    Ready    control-plane   v1.34.2   ...   containerd://2.1.4
w1     Ready    <none>          v1.34.2   ...   containerd://2.1.4
```

On the node itself, check the service and the socket the kubelet was told to use:

```bash
systemctl status containerd --no-pager
grep -r containerRuntimeEndpoint /var/lib/kubelet/config.yaml
cat /var/lib/kubelet/kubeadm-flags.env      # older kubeadm versions keep the flag here
```
</Example>

<Example title="Point crictl at the runtime">
Without configuration, `crictl` tries a list of well-known sockets and prints a warning each time, or fails with
a permission error because the socket belongs to root. Tell it once where to connect, then run it with `sudo`:

```yaml
# /etc/crictl.yaml
runtime-endpoint: unix:///run/containerd/containerd.sock
image-endpoint: unix:///run/containerd/containerd.sock
timeout: 10
```

```bash
sudo crictl version          # proves the connection: prints the runtime name and version
sudo crictl info | grep -i -A3 cgroup
```

For one command only, the flag does the same: `crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps`.
</Example>

<Example title="The API server is down: debug without kubectl">
`kubectl` answers `The connection to the server ... was refused`. The control plane runs as static Pods, so the
containers are on the control plane node, and the runtime can show them even though the API cannot.

```bash
sudo crictl ps -a --name kube-apiserver     # -a includes exited containers
sudo crictl logs <container-id>              # the reason it exited is usually the last line
sudo crictl pods --name kube-apiserver       # is the kubelet still creating the sandbox?
```

A high number in the ATTEMPT column with the state `Exited` means the container starts and crashes in a loop: read
its logs. **No container at all** means the kubelet could not even create it: the manifest in
`/etc/kubernetes/manifests/` is probably invalid YAML, so read the kubelet's log with
`journalctl -u kubelet --since "5 min ago"` instead.
</Example>

<Example title="Follow one Pod from the API down to the process">
The Pod `web` in the namespace `shop` runs on node `w1`. Find its sandbox, its container and its process there:

```bash
sudo crictl pods --namespace shop --name web          # the sandbox: note the POD ID
sudo crictl ps --pod <pod-id>                          # the containers inside it
sudo crictl inspect <container-id> | grep -m1 '"pid"'  # the process ID on the host
ps -fp <pid>                                           # an ordinary Linux process
```

The last command is the point of the whole lesson: a container is a normal process on the node, started by runc
with its own namespaces and cgroup.
</Example>

## Tricks

<Trick title="Filter instead of scrolling">
A control plane node runs dozens of containers. `crictl ps -a --name etcd`, `crictl ps --state exited` and
`crictl pods --namespace kube-system` get you to the right line at once. `crictl ps -a | grep -v Running` is a quick
way to see only what is broken.
</Trick>

<Trick title="Short IDs are enough">
Like Docker, `crictl` accepts any unique prefix of an ID: `crictl logs 3f1` works as long as only one container
starts with `3f1`.
</Trick>

<Trick title="No crictl? Read the log files">
`/var/log/containers/` holds one symlink per container, named `<pod>_<namespace>_<container>-<id>.log`. So
`sudo tail /var/log/containers/kube-apiserver-*` shows why the API server exited without any runtime tool at all.
</Trick>

<Trick title="Free disk space on a node">
A node under disk pressure evicts Pods. `sudo crictl rmi --prune` removes every image that no container uses, and
`sudo crictl imagefsinfo` shows how full the image filesystem is.
</Trick>

<Trick title="If you must use ctr or nerdctl, name the namespace">
Kubernetes containers live in the containerd namespace `k8s.io`: `sudo ctr -n k8s.io containers ls`,
`sudo nerdctl -n k8s.io ps`. Without it you look at an empty namespace and conclude, wrongly, that nothing is running.
</Trick>

## Common mistakes

- **Reaching for `docker ps` on a node.** On a containerd node the command is missing, and where Docker *is*
  installed beside containerd it lists Docker's own containers, not the Pods. Use `crictl`.
- **Thinking images must be rebuilt.** Images built with Docker are OCI images. Nothing about them changes when the
  node runs containerd.
- **Fixing a Pod with crictl.** Stopping or removing a container by hand only makes the kubelet recreate it. Fix the
  cause (the manifest, the image, the config) and let the kubelet do the rest.
- **Forgetting `-a`.** `crictl ps` lists running containers only. A crashed control plane component is not running,
  so without `-a` it looks as if it never existed.
- **Confusing the two kinds of namespace.** `crictl pods --namespace` filters by *Kubernetes* namespace. `ctr -n`
  and `nerdctl -n` choose a *containerd* namespace, which for Kubernetes is always `k8s.io`.
- **Editing containerd's config and not restarting it.** Changes to `/etc/containerd/config.toml` apply after
  `sudo systemctl restart containerd`. Running Pods survive the restart.

## Recap

- Docker is a stack: CLI → dockerd → **containerd** → **runc**. Kubernetes only needs the last two.
- The kubelet talks to runtimes through **CRI**; Docker never implemented it, so dockershim translated until it was
  removed in **v1.24**.
- Images built with Docker still run, because images and runtimes follow the **OCI** specifications.
- On the node a Pod is a **sandbox** (the pause container) plus its containers, supervised by a shim.
- **`crictl`** sees what the kubelet sees and works when the API server is down: `ps -a`, `logs`, `pods`, `inspect`.
