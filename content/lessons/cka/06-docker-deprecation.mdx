## Why this note exists

In December 2020 the Kubernetes v1.20 release notes carried one line that travelled much further than its authors
expected: *"Docker support in the kubelet is now deprecated and will be removed in a future release."* Many people
read it as "Kubernetes is dropping Docker" and worried about their images, their Dockerfiles and their clusters.

What was deprecated, and then removed in **v1.24 (May 2022)**, was something much smaller: **dockershim**, a piece of
adapter code inside the kubelet. Nothing about how you build or ship images changed. What changed is which program
the kubelet talks to on each node, and which commands you use when you log in to a node.

Older tutorials, blog posts and course videos still show `docker ps` on a Kubernetes node. This lesson explains why
that no longer works, so the rest of the course (and the exam's clusters) make sense.

<KeyIdea>
Kubernetes did not remove Docker. It removed **dockershim**, the adapter that let the kubelet drive Docker Engine.
Images built with Docker run exactly as before; only the runtime on the node, and the tool you debug it with, changed.
</KeyIdea>

## What dockershim was

To understand the adapter you need three terms:

| Term | What it is |
|------|------------|
| **CRI** (Container Runtime Interface) | The gRPC API the kubelet uses to tell a runtime "pull this image, create this Pod sandbox, start this container". Introduced in Kubernetes v1.5 so that the kubelet would not need code for each runtime |
| **Docker Engine** (`dockerd`) | The daemon behind the `docker` command. It predates CRI and never implemented it. It has its own API, made for people and tools, not for an orchestrator |
| **dockershim** | Code compiled into the kubelet that accepted CRI calls and translated them into Docker API calls. The only runtime adapter that lived inside Kubernetes itself |

<Diagram id="call-chain" />

The top row is how every Docker-based cluster worked up to v1.23. Notice what sits at the far end of it:
**containerd**. Docker Engine has not run containers itself for years. Docker split its low-level runtime out as
containerd in 2016 and donated it to the CNCF, and `dockerd` has used it ever since. So the kubelet was calling an
adapter, which called Docker, which called the component that could have done the job directly.

The bottom row is every cluster since v1.24: containerd ships with a CRI plugin, so the kubelet talks to it without
a translator. The container that starts is the same in both rows, created by the same `runc`.

## Why it was removed

- **It was vendor code in the kubelet.** Every other runtime implements CRI on its own side. Dockershim was
  Kubernetes maintainers keeping up with another project's API, release after release. The deprecation notice itself
  said it "has seen maintenance issues in the Kubernetes community".
- **Docker Engine does more than Kubernetes needs.** Its own networking, volumes, build system and Swarm mode are
  unused on a node. Kubernetes brings CNI for networking and CSI for storage. Fewer moving parts means fewer things
  to break and patch.
- **New features were built on CRI only.** Work such as cgroup v2 support and user namespaces targets CRI runtimes.
  Each one would have needed extra work in dockershim, or would simply not have reached Docker nodes.
- **The shorter path is cheaper.** Two fewer hops per operation, and one fewer daemon whose restart can
  disturb the node.

<DeepDive title="The timeline, release by release">
- **v1.5 (December 2016):** CRI arrives in alpha. Docker support inside the kubelet is rewritten as the first CRI
  implementation: that is dockershim.
- **2017 to 2019:** containerd gains a CRI plugin (built in from containerd 1.1), CRI-O matures, and managed
  platforms start moving their nodes to containerd.
- **v1.20 (December 2020):** dockershim is deprecated. The blog post "Don't Panic: Kubernetes and Docker" is
  published the same week.
- **v1.24 (May 2022):** dockershim is removed. The kubelet flags that only made sense with it go too:
  `--network-plugin`, `--cni-conf-dir` and `--cni-bin-dir` (CNI is now configured in the runtime).
- **v1.27:** the already meaningless `--container-runtime` kubelet flag is removed. An old kubelet unit file that
  still passes `--container-runtime=remote` now stops the kubelet from starting: a classic upgrade failure.
- **Meanwhile:** Mirantis and Docker took the dockershim code out of the tree and maintain it as the separate
  project **cri-dockerd**.
</DeepDive>

## What still works, and what does not

<Diagram id="image-path" />

"Docker image" is a habit of speech. What `docker build` produces is an image in the **OCI** (Open Container
Initiative) format, and every runtime pulls and runs that format. That is why nothing changed for developers.

| You do this | After dockershim's removal |
|-------------|----------------------------|
| Build images with `docker build` on a laptop or in CI | Works. The cluster never knew how the image was built |
| Pull from Docker Hub or any other registry | Works. Registries serve OCI images to any runtime |
| Use Docker Desktop, kind or minikube locally | Works. kind and minikube run nodes *as* Docker containers, and inside each node the runtime is containerd |
| Run `docker ps` on a node to see Pods' containers | **Breaks.** Docker is not installed, or is installed and shows nothing (see below) |
| Mount `/var/run/docker.sock` into a Pod (CI build jobs, some monitoring and security agents) | **Breaks.** No socket. Build with a daemonless tool such as BuildKit, Kaniko or Buildah, and update agents to versions that use CRI |
| Build an image on the node and run it with `imagePullPolicy: Never` | **Breaks.** The kubelet only sees images in the CRI runtime's store |
| Configure registry mirrors or insecure registries in `/etc/docker/daemon.json` | **Ignored.** Configure them in the runtime instead (for containerd, `/etc/containerd/config.toml` and `/etc/containerd/certs.d/`) |

<DeepDive title="Docker is installed on the node, yet docker ps is empty. Why?">
containerd keeps its containers and images in **namespaces** (containerd's own, unrelated to Kubernetes namespaces).
The kubelet's CRI plugin works in the namespace `k8s.io`; Docker Engine works in `moby`. Both can share one containerd
daemon on the same machine and never see each other's containers or images.

```bash
sudo ctr namespaces list              # k8s.io, and moby if Docker is installed
sudo ctr -n k8s.io containers list    # the kubelet's containers
sudo ctr -n k8s.io images import app.tar   # make a locally built image visible to the kubelet
```

That is also the reason an image you just built with `docker build` on a node gives `ErrImageNeverPull` or
`ImagePullBackOff`: it is in the wrong store. Push it to a registry, or import it into `k8s.io`.
</DeepDive>

## Your choices today

<Diagram id="runtimes-today" />

The kubelet finds its runtime through one setting, the **runtime endpoint**: a Unix socket. Whatever answers CRI on
that socket is the node's runtime.

| Runtime | Socket | Notes |
|---------|--------|-------|
| containerd | `unix:///run/containerd/containerd.sock` | The default choice for kubeadm clusters and most managed services |
| CRI-O | `unix:///var/run/crio/crio.sock` | Built only for Kubernetes; the runtime of OpenShift |
| Docker Engine + cri-dockerd | `unix:///var/run/cri-dockerd.sock` | For nodes that must keep Docker Engine. Both the Docker daemon and the adapter have to be installed and running |

kubeadm detects the socket by itself when only one runtime is installed. With several (for example Docker Engine
plus cri-dockerd on a machine that also has containerd, which is always the case with Docker), it stops and asks
you to choose: pass `--cri-socket unix:///var/run/cri-dockerd.sock` to `kubeadm init` or `kubeadm join`.

<Callout kind="warning" title="containerd from Docker's packages has CRI switched off">
Installing Docker Engine also installs containerd (the `containerd.io` package), but its
`/etc/containerd/config.toml` contains `disabled_plugins = ["cri"]`. `kubeadm init` then fails its preflight check
with *"container runtime is not running ... unknown service runtime.v1.RuntimeService"*. Remove `cri` from that list
(or regenerate the file with `containerd config default`), then `systemctl restart containerd`.
</Callout>

## Using it

<Example title="Find out which runtime a node uses">
From anywhere with `kubectl`:

```bash
kubectl get nodes -o wide          # last column: CONTAINER-RUNTIME
kubectl get node node-1 -o jsonpath='{.status.nodeInfo.containerRuntimeVersion}{"\n"}'
```

```text
containerd://2.1.4
```

The prefix is the runtime: `containerd://`, `cri-o://`, or `docker://` on a node that uses cri-dockerd.

On the node itself, find the socket the kubelet was told to use. It is either the flag
`--container-runtime-endpoint` or the field `containerRuntimeEndpoint` in the kubelet's configuration file:

```bash
ps -ef | grep [k]ubelet | tr ' ' '\n' | grep runtime
sudo grep -ri runtime /var/lib/kubelet/
```
</Example>

<Example title="Debug a control plane that kubectl cannot reach">
`kubectl get nodes` answers "connection refused": the API server is down, so `kubectl` cannot tell you why. On a
kubeadm cluster the API server is a static Pod, which means its container is run by the kubelet through the runtime.
SSH to the control plane node and ask the runtime directly:

```bash
sudo crictl ps -a --name kube-apiserver     # -a also shows exited containers
sudo crictl logs --tail=20 <container-id>   # why did it exit?
sudo crictl pods --name kube-apiserver      # does the Pod sandbox exist at all?
journalctl -u kubelet --since "10 min ago"  # if there is no container, the kubelet says why
```

With Docker this used to be `docker ps -a | grep apiserver` and `docker logs`. The reasoning is the same; only the
tool changed.
</Example>

<Example title="Translate an old Docker habit">
`crictl` deliberately keeps Docker's subcommand names for everything it supports:

| With Docker | With any CRI runtime |
|-------------|----------------------|
| `docker ps -a` | `crictl ps -a` |
| `docker images` | `crictl images` |
| `docker logs -f <id>` | `crictl logs -f <id>` |
| `docker exec -it <id> sh` | `crictl exec -it <id> sh` |
| `docker inspect <id>` | `crictl inspect <id>` (containers), `crictl inspectp <id>` (Pods) |
| `docker pull nginx` | `crictl pull nginx` |
| `docker stats` | `crictl stats` |
| (nothing) | `crictl pods`: list Pod sandboxes |
| `docker build`, `docker push`, `docker run` | Not in `crictl`. It is a debugging tool: create workloads with `kubectl` |
</Example>

## Tricks

<Trick title="Silence crictl's endpoint warnings once">
If `crictl` prints warnings about trying default endpoints, or fails to connect, tell it where the runtime is:

```bash
sudo crictl config --set runtime-endpoint=unix:///run/containerd/containerd.sock
```

That writes `/etc/crictl.yaml`. For a single command, use `crictl --runtime-endpoint <socket> ps` instead.
</Trick>

<Trick title="Read the runtime from the node object">
`kubectl get nodes -o wide` is the fastest answer to "which runtime and version does this node use?", and
`kubectl describe node <name> | grep -i runtime` works when the wide table wraps badly in a small terminal.
</Trick>

<Trick title="Do not fix Pods with crictl">
If you `crictl stop` or `crictl rm` a container that belongs to a Pod, the kubelet notices and creates it again.
That makes `crictl` a quick way to restart one stuck static Pod container, and the wrong way to remove anything.
Change the Pod (or the static Pod manifest) and let the kubelet do the rest.
</Trick>

<Trick title="Translate old answers as you read them">
Much of the troubleshooting advice online predates v1.24. When it says `docker`, on a node read `crictl`; when it
says to edit `/etc/docker/daemon.json`, read `/etc/containerd/config.toml`; when it says `systemctl restart docker`,
read `systemctl restart containerd`.
</Trick>

## Common mistakes

- **Saying "Kubernetes no longer supports Docker images".** It does. The image format is OCI and was never the issue.
- **Looking for containers with `docker ps` on a node.** Empty output does not mean nothing is running. Use
  `crictl ps`.
- **Building an image on the node and expecting Pods to find it.** The kubelet only sees the CRI runtime's image
  store. Push to a registry, or import with `ctr -n k8s.io images import`.
- **Installing Docker Engine and forgetting cri-dockerd.** From v1.24 the kubelet cannot use Docker Engine on its
  own; `kubeadm init` finds no usable CRI socket, or finds containerd with its CRI plugin disabled.
- **Keeping removed kubelet flags through an upgrade.** `--container-runtime` and `--network-plugin` in an old unit
  file or `/var/lib/kubelet/kubeadm-flags.env` make a newer kubelet exit at start. `journalctl -u kubelet` shows
  "unknown flag".
- **Confusing CRI with OCI.** CRI is how the kubelet talks to a runtime. OCI is the format of images and the
  low-level contract for running a container. Docker fails the first and fully meets the second.

## Recap

- v1.20 deprecated and **v1.24 removed dockershim**, the kubelet's built-in adapter for Docker Engine. Docker itself
  was not removed from anything.
- Images built with Docker are **OCI images** and run on every runtime.
- The kubelet speaks only **CRI**, over a socket: containerd or CRI-O directly, Docker Engine only through
  **cri-dockerd**.
- Check a node's runtime with `kubectl get nodes -o wide`.
- On a node, use **`crictl`** (`ps`, `pods`, `logs`, `images`) where older guides say `docker`.
