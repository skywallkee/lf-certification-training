## Why Kubernetes needs etcd

The control plane is a set of programs that can crash, restart or move to another machine at any moment: the API
server, the scheduler, the controller manager. None of them keeps anything important on its own disk. That only works
because all of them agree on one place where the truth is written down.

That place is **etcd**, a distributed key-value store. Every object you have ever seen in `kubectl get` output is a
key in etcd: Pods, Deployments, Secrets, nodes, RBAC rules, and the leases that say which controller manager is the
leader. etcd holds both the **desired state** (the `spec` you applied) and the **observed state** (the `status`
that components report back).

<KeyIdea>
etcd is the cluster's only memory. Everything else in the control plane can be restarted or rebuilt from it, and
the API server is the only component that reads or writes it.
</KeyIdea>

This is why an administrator treats etcd differently from every other component. A broken scheduler is an outage
you fix by restarting it. A lost etcd with no backup is a lost cluster: the containers keep running on the nodes for
a while, but Kubernetes no longer knows that they exist.

## What Kubernetes keeps in etcd

<Diagram id="only-api-server" />

The scheduler, the controller manager, the kubelet and `kubectl` all get their view of the cluster from the API
server. Not one of them has the address of etcd or a certificate to open a connection to it. The API server is the
single client, and it talks to etcd over mutual TLS on port **2379**.

The API server stores each object as one key under the `/registry` prefix. The layout is predictable:

| Object | Key in etcd |
|--------|-------------|
| Pod `web` in namespace `shop` | `/registry/pods/shop/web` |
| Deployment `web` in `shop` | `/registry/deployments/shop/web` |
| Secret `db-password` in `shop` | `/registry/secrets/shop/db-password` |
| Namespace `shop` | `/registry/namespaces/shop` |
| ClusterRole `view` (no namespace) | `/registry/clusterroles/view` |
| Node `node01` | `/registry/minions/node01` |
| A custom resource | `/registry/GROUP/PLURAL/NAMESPACE/NAME` |

Nodes live under `minions` because that is what Kubernetes called them in its first releases, and renaming the keys
would have broken every existing cluster.

Just as useful is knowing what is **not** in etcd:

- **Container logs and metrics.** Logs are files on each node, and the metrics server keeps its numbers in memory.
- **The data in your volumes.** etcd stores the PersistentVolume and the claim, which are descriptions. The bytes
  live on the storage system.
- **Container images.** They sit in registries and in each node's image cache.
- **Files on the nodes.** The certificates in `/etc/kubernetes/pki`, the kubeconfig files and the static Pod
  manifests are plain files. An etcd backup does not contain them.

## How the API server uses etcd

<Diagram id="write-and-watch" />

Follow one `kubectl create deployment web --image=nginx -n shop`:

1. `kubectl` sends a POST request to the API server.
2. The API server authenticates the caller, checks RBAC, runs admission and validates the object.
3. It writes the object to etcd at `/registry/deployments/shop/web`. etcd replicates the write to a majority of its
   members and assigns it a new **revision**, a counter that increases with every change to the store.
4. Only now does the API server answer `deployment.apps/web created`. If etcd cannot commit the write, you get an
   error and nothing was created.
5. The Deployment controller, which has a **watch** open on the API server, receives an event and creates a
   ReplicaSet. That is another write to etcd, another event, and so on down to the kubelet starting containers.

Three things you already use every day come straight from this design:

- **`resourceVersion`** in an object's metadata is the etcd revision of its last change.
- **`kubectl get pods --watch`** works because etcd can stream every change after a given revision, and the API
  server passes that stream on. Controllers never poll; they watch.
- **Conflict errors.** When two clients update the same object, the API server tells etcd "write this only if the
  key is still at the revision I read". The second writer loses and sees *the object has been modified; please apply
  your changes to the latest version and try again*. No locks are needed.

<DeepDive title="Details that explain limits you will meet">
- **Values are binary.** Built-in objects are stored as protobuf, not as the YAML or JSON you see in `kubectl`. If
  you read a key with `etcdctl` the value looks like noise with a few readable strings in it. Custom resources are
  stored as JSON.
- **Secrets are not encrypted by default.** A Secret's data is only base64 in the API, and in etcd it is stored
  as it is unless the API server was started with an encryption configuration. Anyone who can read etcd, or a
  snapshot file, can read every Secret. Treat backups accordingly.
- **Objects have a size limit.** etcd rejects requests larger than about 1.5 MiB, which is why a ConfigMap or
  Secret cannot hold more than 1 MiB of data.
- **The database has a size limit too.** etcd stops accepting writes when its database reaches its quota (2 GiB
  unless configured otherwise) and raises a `NOSPACE` alarm. The cluster then looks read-only.
- **History is trimmed.** etcd keeps old revisions of every key so that watches can catch up. The API server asks
  etcd to compact that history every five minutes. A watcher that falls too far behind gets a "resource version too
  old" error and has to list everything again.
- **Events expire.** The API server attaches a one hour lease to each Event, and etcd deletes it when the lease
  runs out. That is why `kubectl get events` only shows the recent past.
</DeepDive>

## How etcd is deployed

There are two ways you will meet etcd in a cluster, and the first question in any etcd task is which one you are
looking at.

| | kubeadm cluster | Installed by hand |
|---|-----------------|-------------------|
| Runs as | A static Pod named `etcd-NODENAME` in `kube-system` | A systemd service on the host |
| Configured in | `/etc/kubernetes/manifests/etcd.yaml` | The unit file, usually `/etc/systemd/system/etcd.service` |
| Started by | The kubelet | systemd |
| See it with | `kubectl -n kube-system get pods`, `crictl ps` | `systemctl status etcd` |
| Logs | `kubectl logs`, `crictl logs` | `journalctl -u etcd` |

The exam clusters are built with kubeadm, so the static Pod is the one to know well.

<Diagram id="kubeadm-etcd" />

A **static Pod** is started by the kubelet directly from a manifest file in `/etc/kubernetes/manifests`. This solves
a chicken and egg problem: the API server cannot start without etcd, so etcd cannot be something the API server
schedules. The Pod you see in `kubectl -n kube-system get pods` is only a mirror that the kubelet publishes. You
cannot change etcd by editing that Pod. You edit the file, and the kubelet restarts etcd when the file changes.

The flags in the manifest answer almost every question you can be asked:

```yaml
spec:
  containers:
    - name: etcd
      image: registry.k8s.io/etcd:3.6.5-0
      command:
        - etcd
        - --name=controlplane
        - --advertise-client-urls=https://192.168.56.10:2379
        - --listen-client-urls=https://127.0.0.1:2379,https://192.168.56.10:2379
        - --listen-peer-urls=https://192.168.56.10:2380
        - --initial-cluster=controlplane=https://192.168.56.10:2380
        - --data-dir=/var/lib/etcd
        - --cert-file=/etc/kubernetes/pki/etcd/server.crt
        - --key-file=/etc/kubernetes/pki/etcd/server.key
        - --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
        - --client-cert-auth=true
        - --peer-cert-file=/etc/kubernetes/pki/etcd/peer.crt
        - --peer-key-file=/etc/kubernetes/pki/etcd/peer.key
        - --peer-trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
        - --listen-metrics-urls=http://127.0.0.1:2381
      volumeMounts:
        - { name: etcd-data, mountPath: /var/lib/etcd }
        - { name: etcd-certs, mountPath: /etc/kubernetes/pki/etcd }
  hostNetwork: true
  volumes:
    - name: etcd-data
      hostPath: { path: /var/lib/etcd, type: DirectoryOrCreate }
    - name: etcd-certs
      hostPath: { path: /etc/kubernetes/pki/etcd, type: DirectoryOrCreate }
```

| Flag | What it tells you |
|------|-------------------|
| `--listen-client-urls` | Where clients connect: the API server and `etcdctl`. Port **2379** |
| `--listen-peer-urls` | Where other etcd members connect to replicate. Port **2380** |
| `--data-dir` | The folder that holds the database, and the thing a backup protects |
| `--cert-file`, `--key-file` | The certificate etcd shows to clients |
| `--trusted-ca-file` | The CA that client certificates must be signed by |
| `--client-cert-auth=true` | Clients must present a certificate: there are no anonymous connections |
| `--initial-cluster` | The members this one expects to find: one entry on a single node cluster |
| `--listen-metrics-urls` | A plain HTTP health and metrics port on localhost, **2381**, used by the Pod's probes |

The other half of the connection is in the API server's own manifest,
`/etc/kubernetes/manifests/kube-apiserver.yaml`:

```yaml
- --etcd-servers=https://127.0.0.1:2379
- --etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
- --etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
- --etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
```

<Callout kind="warning" title="etcd has its own certificate authority">
kubeadm creates two separate CAs. `/etc/kubernetes/pki/ca.crt` signs the cluster's certificates, and
`/etc/kubernetes/pki/etcd/ca.crt` signs everything that touches etcd. Passing the cluster CA to `etcdctl` fails with
"certificate signed by unknown authority". If a path has no `etcd` in it, it is almost certainly the wrong file.
</Callout>

## Topologies: stacked and external

A single etcd member is fine for practice and is what most exam clusters have. In production you run several
members so that the cluster survives a machine failure. kubeadm supports two layouts.

<Diagram id="stacked-etcd" />

In the **stacked** topology, the default, every control plane node runs an etcd member next to its API server.
`kubeadm join --control-plane` adds the new member for you. Each API server points at `https://127.0.0.1:2379`, its
local member. It is simple and needs no extra machines, but a node failure costs you an API server and an etcd
member at the same moment.

<Diagram id="external-etcd" />

In the **external** topology the members run on their own hosts, and you tell kubeadm about them in its
configuration file. Every API server then lists all of them:

```yaml
- --etcd-servers=https://10.0.1.11:2379,https://10.0.1.12:2379,https://10.0.1.13:2379
```

| | Stacked | External |
|---|---------|----------|
| Machines for a highly available control plane | 3 | 6 (3 control plane, 3 etcd) |
| etcd Pods in `kube-system` | Yes, one per control plane node | None |
| `--etcd-servers` on the API server | `https://127.0.0.1:2379` | A list of other hosts |
| A control plane node fails | Lose one API server and one member | Lose one API server only |

### Quorum

etcd members elect a leader and accept a write only when a **majority** of members, the quorum, has stored it. That
rule is what keeps two halves of a split cluster from both accepting different writes. It also decides how many
failures you can afford:

| Members | Quorum | Failures tolerated |
|---------|--------|--------------------|
| 1 | 1 | 0 |
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |

<Callout kind="warning" title="Two is worse than one">
An even number of members never helps. Two members need both to be up, so you have doubled the chance of an outage
compared with one. Four tolerate one failure, exactly like three. Use three or five.
</Callout>

When quorum is lost, or the single member is down, the API server cannot read or write. `kubectl` returns errors or
times out, nothing new is scheduled and nothing heals. The Pods that are already running **keep running**, because
the kubelet and the container runtime do not need etcd to keep a container alive. The cluster is frozen, not gone.

## Using it

<Example title="Find out how etcd runs on this cluster">
A task asks for the etcd version, its data directory, or the certificate it serves. Start by finding out which kind
of etcd you have:

```bash
kubectl -n kube-system get pods -l component=etcd -o wide
```

A Pod named `etcd-controlplane` means a kubeadm static Pod, and stacked etcd. Now read the facts instead of
remembering them. On the control plane node:

```bash
sudo grep -E 'image:|data-dir|listen-client|-file' /etc/kubernetes/manifests/etcd.yaml
sudo grep etcd /etc/kubernetes/manifests/kube-apiserver.yaml
```

If you are not on the node, `kubectl -n kube-system describe pod etcd-controlplane` shows the same command line.

No etcd Pod at all? Look at `--etcd-servers` in the API server manifest. Addresses of other machines mean external
etcd, and on those machines `systemctl status etcd` and `systemctl cat etcd` show the service and its flags.
</Example>

<Example title="See the keys Kubernetes wrote">
The etcd image ships with `etcdctl`, so you can run it inside the Pod, where the certificates are already mounted.
List the namespaces as etcd sees them:

```bash
kubectl -n kube-system exec etcd-controlplane -- etcdctl \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/namespaces --prefix --keys-only
```

```text
/registry/namespaces/default

/registry/namespaces/kube-node-lease

/registry/namespaces/kube-public

/registry/namespaces/kube-system

/registry/namespaces/shop
```

The three files are the same ones the etcd flags name: `--trusted-ca-file` becomes `--cacert`, `--cert-file` becomes
`--cert` and `--key-file` becomes `--key`. `etcdctl` connects to `127.0.0.1:2379` unless you pass `--endpoints`,
which is right inside the Pod. Leave out `--keys-only` and you get the protobuf values as well.

Reading is safe. Never write or delete keys by hand: the API server is the only writer that keeps objects valid.
</Example>

<Example title="Check etcd when the cluster misbehaves">
While the API server still answers, ask it about its etcd connection:

```bash
kubectl get --raw='/readyz/etcd'
kubectl -n kube-system logs etcd-controlplane --tail=20
```

When `kubectl` itself fails with "connection refused" or a timeout, go to the control plane node. The static Pods
do not need the API server, and neither does the container runtime's own tool:

```bash
sudo crictl ps -a --name etcd              # running, or exited and restarting?
sudo crictl logs CONTAINER_ID              # why it stopped
sudo journalctl -u kubelet --since "10 min ago" | grep -i etcd
```

Typical causes: a typo in a flag in `etcd.yaml`, a certificate path that does not exist, a `--data-dir` that
does not match the volume, or a full disk. Fix the manifest and the kubelet restarts the Pod within a minute.
</Example>

## Tricks

<Trick title="Let the manifest give you the etcdctl flags">
You do not need to remember any path. `grep -- '-file' /etc/kubernetes/manifests/etcd.yaml` prints the CA, the
certificate and the key, and `grep listen-client` prints the endpoint. Copy them into your `etcdctl` command.
</Trick>

<Trick title="A path lives in three places">
The data directory appears as the `--data-dir` flag, as the container's `volumeMounts` path, and as the `hostPath`
of the `etcd-data` volume. The flag and the mount path are inside the container, the `hostPath` is on the node. To
point etcd at another folder on the node, changing only the `hostPath` is enough. If you change the flag, change the
mount to match.
</Trick>

<Trick title="Stop a static Pod by moving its manifest">
There is no `kubectl delete` that keeps a static Pod down. Move the file out of the folder and the kubelet stops the
Pod; move it back and it starts again:

```bash
sudo mv /etc/kubernetes/manifests/etcd.yaml /tmp/
sudo mv /tmp/etcd.yaml /etc/kubernetes/manifests/
```
</Trick>

<Trick title="Stacked or external in ten seconds">
`kubectl -n kube-system get pods | grep etcd`. One Pod per control plane node means stacked. No Pods, and
`--etcd-servers` pointing at other hosts, means external.
</Trick>

## Common mistakes

- **Thinking other components use etcd.** Only the API server does. A scheduler that cannot schedule is never a
  scheduler to etcd connection problem.
- **Mixing up the ports.** 2379 is for clients, 2380 is for members talking to each other. `etcdctl` on 2380 fails
  with a TLS or deadline error.
- **Using the wrong CA or certificate.** The etcd files are under `/etc/kubernetes/pki/etcd/`. The API server's
  client pair, `apiserver-etcd-client`, sits one folder up.
- **Editing the mirror Pod.** `kubectl edit pod etcd-controlplane` changes nothing that lasts. Edit the manifest
  file.
- **Leaving a copy in the manifests folder.** The kubelet runs every file it finds there, so `etcd.yaml.bak` next
  to `etcd.yaml` starts a second, conflicting etcd. Keep backups of manifests somewhere else.
- **Expecting a backup of etcd to hold everything.** It holds every API object, but not volume data and not the
  certificates and manifests on the node.

## Recap

- etcd holds all cluster state, one key per object under `/registry`; lose it without a backup and the cluster is gone.
- Only the API server talks to etcd, on port 2379 with its own client certificate.
- On kubeadm clusters etcd is a static Pod: `/etc/kubernetes/manifests/etcd.yaml`, data in `/var/lib/etcd`,
  certificates in `/etc/kubernetes/pki/etcd`.
- Stacked puts a member on every control plane node; external uses separate hosts. Either way, writes need quorum,
  so run three or five members.
- When `kubectl` fails, use `crictl` on the control plane node, and read every path from the manifest.
