## Why you need etcd commands

On a normal day nobody talks to etcd except the API server. You run `kubectl`, the API server checks and stores the
object, and etcd is an implementation detail. That stops being true in exactly the situations a cluster
administrator is paid for:

- **Before an upgrade or a risky change**, you want a backup of the whole cluster state. The cluster state *is*
  etcd, so the backup is an etcd snapshot.
- **When the control plane misbehaves**, `kubectl` may hang or fail, and you need to know whether etcd itself is
  healthy without going through the API server.
- **After a disaster**, restoring a snapshot is the only way to get the cluster's objects back.

All three are done with etcd's own command line tools, not with `kubectl`.

<KeyIdea>
`etcdctl` is a client, just like the API server is. Give it the same three things the API server has (an endpoint,
a CA to trust and a client certificate with its key) and it can ask etcd anything. Every long etcdctl command is
those three things plus a two-word subcommand.
</KeyIdea>

## The two tools and the API version

etcd ships two tools, and knowing which one a job belongs to removes most of the confusion:

| Tool | Talks to | Needs certificates | Used for |
|------|----------|--------------------|----------|
| `etcdctl` | A **running** etcd, over the network | Yes | Health, members, reading keys, `snapshot save`, defragmenting |
| `etcdutl` | **Files** on disk, no server involved | No | `snapshot status`, `snapshot restore`, offline maintenance |

The split is recent. Up to etcd 3.5, `etcdctl snapshot restore` and `etcdctl snapshot status` existed and printed a
deprecation warning; from etcd 3.6 they are removed, and only `etcdutl` restores. If a command from an older guide
answers `unknown command "restore"`, this is why.

The other thing old guides get wrong is the **API version**. etcd had a v2 API with a different data model and
different commands. Kubernetes only ever uses v3, and etcdctl has defaulted to v3 since etcd 3.4.

| | API v2 (old guides) | API v3 (what you use) |
|---|---|---|
| Write and read | `etcdctl set`, `get`, `ls`, `rm` | `etcdctl put`, `get`, `del` |
| Health | `etcdctl cluster-health` | `etcdctl endpoint health` |
| Backup | `etcdctl backup` | `etcdctl snapshot save` |
| TLS flags | `--ca-file`, `--cert-file`, `--key-file` | `--cacert`, `--cert`, `--key` |

<Callout kind="note" title="About ETCDCTL_API=3">
Many guides, and the Kubernetes documentation, still start commands with `ETCDCTL_API=3`. It was needed when
etcdctl defaulted to v2. Today it changes nothing, so it is harmless to keep and safe to leave out. Check what you
have with `etcdctl version`.
</Callout>

## How a command reaches etcd

<Diagram id="etcdctl-path" />

etcd listens for clients on port **2379** (port 2380 is for the members talking to each other). On a kubeadm
cluster it runs as a static Pod on the control plane node, on the host network, so from a shell on that node it is
reachable at `https://127.0.0.1:2379`.

etcd is started with `--client-cert-auth=true`. That means TLS in both directions: etcdctl checks etcd's
certificate against a CA, and etcd refuses any client that does not present a certificate signed by its own CA.
That is why a bare `etcdctl member list` just hangs and times out on a real cluster.

You never have to remember the paths. Each etcdctl flag has a twin among the flags etcd itself was started with,
and those are in the static Pod manifest:

| etcd server flag (in `etcd.yaml`) | etcdctl flag | Environment variable | kubeadm default |
|---|---|---|---|
| `--listen-client-urls` | `--endpoints` | `ETCDCTL_ENDPOINTS` | `https://127.0.0.1:2379` |
| `--trusted-ca-file` | `--cacert` | `ETCDCTL_CACERT` | `/etc/kubernetes/pki/etcd/ca.crt` |
| `--cert-file` | `--cert` | `ETCDCTL_CERT` | `/etc/kubernetes/pki/etcd/server.crt` |
| `--key-file` | `--key` | `ETCDCTL_KEY` | `/etc/kubernetes/pki/etcd/server.key` |

Every etcdctl flag can be given as an environment variable instead: upper-case the flag name, turn dashes into
underscores and put `ETCDCTL_` in front.

<DeepDive title="Why the server's certificate works as a client certificate">
It looks odd to hand etcdctl the *server's* certificate. It works because kubeadm issues `server.crt` for both
server and client authentication, and all etcd asks of a client is a certificate signed by the etcd CA. Two other
pairs signed by the same CA work just as well:

- `/etc/kubernetes/pki/etcd/healthcheck-client.crt` and `.key`, made for health checks.
- `/etc/kubernetes/pki/apiserver-etcd-client.crt` and `.key`, the pair the API server itself uses (look for
  `--etcd-certfile` in `kube-apiserver.yaml`).

Note that etcd has **its own CA** (`pki/etcd/ca.crt`), separate from the cluster CA in `pki/ca.crt`. Passing the
cluster CA is a classic way to get `x509: certificate signed by unknown authority`.
</DeepDive>

<DeepDive title="Three places to run etcdctl from">
- **On the control plane node**, if etcdctl is installed there. The certificate files are on the node's disk, so
  the paths in the table work as they are.
- **Inside the etcd Pod**: `kubectl -n kube-system exec etcd-controlplane -- etcdctl ...`. The Pod mounts
  `/etc/kubernetes/pki/etcd` at the same path, so the same flags work. The image is minimal and may have no shell,
  so call `etcdctl` directly instead of through `sh -c`, and pass flags rather than relying on your own shell's
  environment variables. A file you write there (a snapshot, for example) lands inside the container unless you
  write it under a mounted path such as `/var/lib/etcd`.
- **Through the container runtime**, when the API server is down and `kubectl` no longer answers:
  `crictl ps --name etcd` gives the container id, and `crictl exec <id> etcdctl ...` runs the command. This works
  because the kubelet and the runtime keep static Pods running without the API server.
</DeepDive>

## The commands, by job

| Job | Command | What it tells you or does |
|-----|---------|---------------------------|
| Is etcd alive? | `etcdctl endpoint health` | Commits a test proposal: healthy means a write still gets through |
| How is it doing? | `etcdctl endpoint status -w table` | Version, database size, leader, Raft term and index per endpoint |
| Who is in the cluster? | `etcdctl member list -w table` | Each member's id, name, peer and client URLs |
| List keys | `etcdctl get /registry --prefix --keys-only` | Every key Kubernetes has written |
| Read one key | `etcdctl get <key>` | The key and its value (binary for Kubernetes objects) |
| Follow changes | `etcdctl watch <key> --prefix` | Prints every PUT and DELETE as it happens |
| Back up | `etcdctl snapshot save <file>` | A consistent copy of the whole keyspace in one file |
| Check a backup | `etcdutl snapshot status <file> -w table` | Hash, revision, key count and size of the file |
| Restore | `etcdutl snapshot restore <file> --data-dir <dir>` | Builds a new data directory from the file |
| Reclaim space | `etcdctl defrag` | Gives freed space in the database file back to the disk |
| Find alarms | `etcdctl alarm list` | Shows `NOSPACE` when the database hit its size quota |

Add `--cluster` to the `endpoint` commands to ask every member instead of only the endpoints you named. `-w` sets
the output format: `simple` (the default), `table`, `json` or `fields`.

### What Kubernetes stores, and where

<Diagram id="key-layout" />

The API server keeps every object as one key under the `/registry` prefix: `/registry/<resource>/<namespace>/<name>`,
or `/registry/<resource>/<name>` for cluster-scoped resources. A few names are historical: nodes live under
`/registry/minions`, and Services under `/registry/services/specs`.

The values are not YAML. They are the objects in Kubernetes' binary protobuf encoding, starting with the bytes
`k8s`. You can spot names and image strings in the output, but to *read* an object you still use `kubectl`. What
etcdctl is good for here is proving that something exists (or does not) at the storage level, counting keys, and
watching the API server work.

<Callout kind="warning" title="Read, do not write">
`etcdctl put` and `etcdctl del` work on `/registry` keys, and nothing stops you. But a write that bypasses the API
server skips validation, admission, defaulting, finalizers and garbage collection, and can leave objects no
component can decode. On a Kubernetes cluster, treat etcdctl as read-only, plus snapshots and maintenance.
</Callout>

<DeepDive title="Why a healthy etcd can still refuse writes">
etcd keeps old revisions of every key until they are **compacted**, and the space compaction frees stays inside the
database file until you **defragment**. The file also has a size quota (`--quota-backend-bytes`, 2 GB by default).
When it is reached, etcd raises a `NOSPACE` alarm and accepts only reads and deletes: the API server then fails
every write with `etcdserver: mvcc: database space exceeded`, while `endpoint health` may still look fine.

The API server compacts old revisions on its own every five minutes, so on a Kubernetes cluster the usual fix is
`etcdctl defrag` (one member at a time, because a member blocks while it defragments) followed by
`etcdctl alarm disarm`. Compare `DB SIZE` with the in-use size in `endpoint status` to see how much a defrag
would reclaim.
</DeepDive>

## Backup and restore

<Diagram id="backup-restore" />

`snapshot save` asks the running server for a point-in-time copy of its database and streams it into one file. It
is safe on a live cluster, and the file carries an integrity hash at the end. `snapshot restore` does not put data
back *into* a running etcd. It unpacks the file into a **new data directory**, and you then start etcd on that
directory. Until etcd is pointed at it, nothing has changed.

<DeepDive title="What restore does to cluster identity">
A restore writes new member and cluster ids into the new directory, on purpose: a restored member can then never
rejoin the old cluster by accident and mix two histories. For a single control plane node the defaults are enough.
In a cluster with several etcd members, every member is restored from the **same** snapshot file with its own
`--name`, `--initial-cluster`, `--initial-cluster-token` and `--initial-advertise-peer-urls`, and all of them start
on their new directories together.

A database file copied straight out of a data directory (`member/snap/db`) has no integrity hash, so restoring it
needs `--skip-hash-check`. A file made with `snapshot save` never does.
</DeepDive>

## Using it

All four examples run in a root shell on the control plane node of a kubeadm cluster.

<Example title="Find the flags and check that etcd is healthy">
Read the endpoint and the three file paths from the manifest, export them once, then ask.

```bash
grep -E 'listen-client-urls|trusted-ca-file|cert-file|key-file|data-dir' /etc/kubernetes/manifests/etcd.yaml

export ETCDCTL_ENDPOINTS=https://127.0.0.1:2379
export ETCDCTL_CACERT=/etc/kubernetes/pki/etcd/ca.crt
export ETCDCTL_CERT=/etc/kubernetes/pki/etcd/server.crt
export ETCDCTL_KEY=/etc/kubernetes/pki/etcd/server.key

etcdctl endpoint health
etcdctl endpoint status -w table
etcdctl member list -w table
```

The grep also matches `--peer-cert-file` and `--peer-key-file`. Those are for member-to-member traffic on port
2380; ignore them. If the manifest is not readable, `kubectl -n kube-system describe pod etcd-<node-name>` shows
the same command line.
</Example>

<Example title="See what the API server writes">
With the variables from the first example still set, look at the storage behind the objects you know.

```bash
etcdctl get /registry --prefix --keys-only | head -20       # a sample of everything
etcdctl get /registry/pods --prefix --keys-only              # every Pod, all namespaces
etcdctl get /registry/pods/shop --prefix --count-only --write-out=fields   # how many in one namespace
etcdctl watch /registry/pods/shop --prefix                   # leave running; Ctrl+C to stop
```

In a second terminal, run `kubectl -n shop run tmp --image=nginx:1.29-alpine` and watch several `PUT` events for
the same key arrive: the object is created, then scheduled, then its status is updated. Delete the Pod and a
`DELETE` follows.
</Example>

<Example title="Take a snapshot and prove it is good">
Save the snapshot to the path the task names, then verify it. A backup you have not checked is a hope, not a
backup.

```bash
etcdctl snapshot save /opt/backup/etcd.db
etcdutl snapshot status /opt/backup/etcd.db -w table
```

The same thing without environment variables, as one command you can paste anywhere:

```bash
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/backup/etcd.db
```

`snapshot status` needs no certificates, because it only reads the file. A snapshot is a full copy of the cluster's
objects, Secrets included, so treat the file as you would the cluster's credentials.
</Example>

<Example title="Restore a snapshot on a kubeadm control plane">
Restore into a new directory, then make etcd use it.

```bash
etcdutl snapshot restore /opt/backup/etcd.db --data-dir /var/lib/etcd-restore
```

Now edit `/etc/kubernetes/manifests/etcd.yaml` and change the **hostPath** of the data volume. Leave the
`--data-dir` flag and the `volumeMounts` alone: the container still sees `/var/lib/etcd`, it is the directory on
the host behind that path that changes.

```yaml
  volumes:
    - hostPath:
        path: /var/lib/etcd-restore     # was /var/lib/etcd
        type: DirectoryOrCreate
      name: etcd-data
```

The kubelet notices the changed manifest and recreates the etcd Pod; give it a minute.

```bash
crictl ps --name etcd            # the container is back and its age is seconds
etcdctl endpoint health
kubectl get pods -A              # objects are as they were at the snapshot
```

The other control plane components were talking to the old data. If `kubectl` shows stale or odd state, restart
them by moving their manifests out of `/etc/kubernetes/manifests` and back, and run `systemctl restart kubelet`.
</Example>

## Tricks

<Trick title="Never type a certificate path from memory">
`grep -E 'listen-client|trusted-ca|cert-file|key-file' /etc/kubernetes/manifests/etcd.yaml` prints all four values.
Copy them. A task may also run etcd with different paths or a different port on purpose, and the manifest is the
only place that tells you.
</Trick>

<Trick title="Export once, then type short commands">
The four `ETCDCTL_` variables turn every later command into two or three words. Use either the variables or the
flags, not both for the same setting, and remember the variables are gone in a new shell or after `sudo -i`.
</Trick>

<Trick title="Let the help text write the command">
`etcdctl snapshot save -h` and `etcdutl snapshot restore -h` list every flag with an example. That is faster than
searching the documentation, and it matches the version actually installed.
</Trick>

<Trick title="No etcdctl on the node? Use the one in the Pod">
`kubectl -n kube-system exec etcd-controlplane -- etcdctl --cacert=... --cert=... --key=... endpoint health` works
with the same paths, because the Pod mounts the certificate directory. Save snapshots under `/var/lib/etcd/` in the
Pod so the file appears on the host, then move it where the task wants it.
</Trick>

<Trick title="Check whether Secrets are encrypted at rest">
`etcdctl get /registry/secrets/shop/db-password | hexdump -C` shows the Secret's value in clear text unless
encryption at rest is configured. With it, the value starts with `k8s:enc:` and the provider's name, such as
`k8s:enc:aescbc:v1:`. This is the check the Kubernetes documentation itself uses.
</Trick>

## Common mistakes

- **A command that hangs, then `context deadline exceeded`.** The TLS flags are missing, or the endpoint says
  `http://` instead of `https://`. etcd does not answer clients it cannot authenticate.
- **`certificate signed by unknown authority`.** You passed the cluster CA (`pki/ca.crt`) instead of etcd's own CA
  (`pki/etcd/ca.crt`).
- **`unknown command "restore"` or `"status"`.** The etcdctl on this machine is 3.6 or newer: use `etcdutl` for
  `snapshot restore` and `snapshot status`.
- **Restoring into the live data directory.** Restore refuses a directory that already has data, and deleting
  `/var/lib/etcd` under a running etcd destroys the cluster. Always restore to a new directory and switch over.
- **Restoring and stopping there.** The restore only creates a directory. Until the hostPath in `etcd.yaml` points
  at it, etcd keeps serving the old data and `kubectl` shows no change.
- **Changing the wrong line in the manifest.** Editing `--data-dir` without the matching volume and mount makes etcd
  write inside the container, where the data is lost on the next restart. Change the hostPath only.
- **Saving the snapshot inside the container.** With `kubectl exec`, `/opt/backup/etcd.db` is a path in the
  container, not on the node, and it disappears with the container.

## Recap

- `etcdctl` talks to a running etcd and needs an endpoint, a CA, a certificate and a key; `etcdutl` works on files
  and needs none of them.
- All four values are in `/etc/kubernetes/manifests/etcd.yaml`; export them as `ETCDCTL_` variables once.
- `endpoint health`, `endpoint status -w table` and `member list` answer whether etcd is well.
- Kubernetes objects are keys under `/registry`; read them freely, but leave the writing to the API server.
- Backup is `etcdctl snapshot save`; restore is `etcdutl snapshot restore` into a new directory, then point the
  etcd manifest's hostPath at it.
