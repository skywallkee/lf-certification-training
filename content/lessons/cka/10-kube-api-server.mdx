## Why the API server exists

A cluster is many programs on many machines: a scheduler, controllers, a kubelet on every node, and you with
`kubectl`. All of them need the same picture of what *should* be running. That picture lives in etcd, but if every
program read and wrote etcd directly, each one would need its own access rules, its own validation and its own way
of learning about changes. One bug in one client could corrupt the cluster's state.

So Kubernetes puts a single program in front of the data: **kube-apiserver**. It is the only component that talks
to etcd. Everything else, including the rest of the control plane, is a client that sends it HTTPS requests. That
gives the cluster one place to check who is calling, decide what they may do, refuse objects that make no sense,
and tell everyone who is interested when something changes.

<KeyIdea>
The API server is the front door of the cluster and the only client of etcd. Every component, and every `kubectl`
command, works by reading, writing or watching objects through it. If it is down, the cluster keeps running what it
has, but nothing can change.
</KeyIdea>

## What the API server is

<Diagram id="api-hub" />

The API server is a **stateless REST server**. It keeps no data of its own: every object you have ever applied is
in etcd, and the API server is the gatekeeper and translator in front of it. Four jobs are worth knowing by name:

- **It serves the Kubernetes API.** Every resource is a URL. Core resources live under `/api/v1`, everything else
  under `/apis/<group>/<version>`. `kubectl get pods -n shop` is a `GET` to `/api/v1/namespaces/shop/pods`, and
  `kubectl get deployments -n shop` is a `GET` to `/apis/apps/v1/namespaces/shop/deployments`.
- **It guards the door.** Each request is authenticated, authorized and passed through admission control before it
  can touch the data (the next section follows one through).
- **It stores and versions objects.** It validates an object, writes it to etcd, and stamps it with a
  `resourceVersion` so that two writers cannot silently overwrite each other.
- **It notifies watchers.** Clients can keep a `watch` request open and receive every change as it happens. This is
  how the scheduler learns about a new Pod and how the kubelet learns it must start one.

That last point explains how the whole cluster cooperates. **No component gives another component orders.** When you
create a Deployment, the Deployment controller sees it through its watch and creates a ReplicaSet; the ReplicaSet
controller sees that and creates Pods; the scheduler sees Pods without a node and writes a node name into each; the
kubelet on that node sees a Pod assigned to it and starts the containers. Every step is "watch the API server, do
one small thing, write the result back".

<Callout kind="note" title="It also reaches out">
Most connections go *to* the API server, but a few go the other way. `kubectl logs`, `kubectl exec` and
`kubectl port-forward` are requests to the API server, which then connects to the kubelet on the Pod's node (port
10250) and relays the stream. That is why these commands fail when the control plane cannot reach a node, even
though `kubectl get pods` still works.
</Callout>

## How a request travels through it

<Diagram id="request-path" />

Every request passes the same stations, in the same order. Knowing the order tells you where an error comes from.

1. **Authentication: who are you?** The API server tries its authenticators in turn: client certificates (the
   certificate's common name is the user name, its organizations are the groups), bearer tokens such as
   ServiceAccount tokens, and others such as OIDC. Kubernetes has **no User object**: a user is whatever name a
   trusted credential carries. If nothing accepts the credential, the answer is `401 Unauthorized`.
2. **Authorization: may you do this?** The request is reduced to a few facts (user, groups, verb, resource,
   namespace) and shown to the authorizers listed in `--authorization-mode`, in order. kubeadm sets `Node,RBAC`: the
   Node authorizer covers what kubelets need, and RBAC covers everything else. If no authorizer allows the request,
   the answer is `403 Forbidden`.
3. **Mutating admission.** Admission plugins that may *change* the object run first. This is where a Pod gets its
   default ServiceAccount and token volume, where a LimitRange fills in missing requests and limits, and where a
   PersistentVolumeClaim gets the default StorageClass.
4. **Schema validation.** The object, as it now stands, is checked against the API's schema: required fields, types,
   allowed values. A failure is `422 Unprocessable Entity`, shown by kubectl as `The Pod "x" is invalid: ...`.
5. **Validating admission.** Plugins that may only say yes or no run last, so they judge the final object.
   ResourceQuota, Pod Security admission and validating webhooks live here.
6. **Persistence.** The object is written to etcd, the client gets `201 Created`, and every open watch for that
   resource receives an event.

Reads (`get`, `list`, `watch`) stop after step 2: **admission only sees requests that create, update, delete or
connect**. So admission can stop you from creating a Pod, but it can never hide one from you.

<DeepDive title="Details that explain odd behaviour">
- **Authorizers can pass.** Each authorizer answers allow, deny or "no opinion". The first allow or deny wins; a
  request that nobody has an opinion about is denied. RBAC itself has no deny rules: it only allows, so a missing
  permission is always a missing Role or binding, never a rule that forbids.
- **Anonymous requests.** A request with no credentials at all is not rejected at once. It becomes the user
  `system:anonymous` and is then judged by authorization, which is why an unauthenticated `curl` to most paths
  returns 403 rather than 401, while `/livez`, `/readyz` and `/version` answer.
- **Two kinds of "forbidden".** RBAC and admission can both answer 403. Read the message: RBAC says
  `User "jane" cannot create resource "pods" in API group "" in the namespace "shop"`; admission names the reason,
  for example `exceeded quota` or `violates PodSecurity`.
- **Conflicts.** Every object carries a `resourceVersion`. An update that is based on an old version is refused with
  `409 Conflict` (the "object has been modified" error), and the client must read the object again and retry. This
  is how many controllers can safely edit the same objects without locks.
- **Watches are cheap.** The API server keeps a recent window of changes in memory (the watch cache) and serves most
  lists and watches from it, so thousands of watchers do not turn into thousands of etcd queries.
- **High availability.** Because it is stateless, you can run several API servers behind a load balancer and all of
  them serve traffic at once. The controller manager and the scheduler are different: several copies may run, but
  only the elected leader acts.
</DeepDive>

## How it is installed and configured

How you configure the API server depends on how it was installed.

| Installed with | Runs as | Where the flags are |
|----------------|---------|---------------------|
| kubeadm (the exam's clusters) | A **static Pod** started by the kubelet | `/etc/kubernetes/manifests/kube-apiserver.yaml` |
| Binaries by hand ("the hard way") | A systemd service | `/etc/systemd/system/kube-apiserver.service` |

On any node you can also see the running flags with `ps -ef | grep kube-apiserver`.

<Diagram id="static-pod" />

A static Pod solves a chicken-and-egg problem: Pods are normally created through the API, but the API server cannot
create itself. So the kubelet reads manifests from a folder on disk and runs them without asking anyone. For each
one it also reports a **mirror Pod** to the API, named after the node (`kube-apiserver-cp1`), so that you can see it
and read its logs with kubectl. The file is the truth; the mirror Pod is a reflection. `kubectl delete pod` on it
changes nothing, and `kubectl edit` cannot change the flags.

The flags you are most likely to read or change:

| Flag | What it controls | kubeadm sets |
|------|------------------|--------------|
| `--advertise-address` | The IP other components use to reach this API server | The node's IP |
| `--secure-port` | The HTTPS port | `6443` |
| `--etcd-servers` | Where etcd is (client port) | `https://127.0.0.1:2379` |
| `--etcd-cafile`, `--etcd-certfile`, `--etcd-keyfile` | TLS towards etcd | Files under `/etc/kubernetes/pki` |
| `--client-ca-file` | The CA whose client certificates are trusted | `/etc/kubernetes/pki/ca.crt` |
| `--tls-cert-file`, `--tls-private-key-file` | The API server's own serving certificate | `apiserver.crt`, `apiserver.key` |
| `--kubelet-client-certificate`, `--kubelet-client-key` | How it proves itself to kubelets (logs, exec) | `apiserver-kubelet-client.*` |
| `--authorization-mode` | The authorizers, in order | `Node,RBAC` |
| `--enable-admission-plugins` | Plugins to add to the default set | `NodeRestriction` |
| `--service-cluster-ip-range` | The range Service IPs are taken from | `10.96.0.0/12` |
| `--service-node-port-range` | The range for NodePorts | not set (default `30000-32767`) |
| `--service-account-key-file`, `--service-account-issuer` | Checking and issuing ServiceAccount tokens | `sa.pub`, the cluster's issuer URL |

<Callout kind="warning" title="A flag that names a file needs a volume too">
The API server runs in a container. A flag such as `--audit-policy-file=/etc/kubernetes/audit/policy.yaml` only
works if that path is also mounted into the container with a `hostPath` volume and a `volumeMount`. kubeadm mounts
`/etc/kubernetes/pki` for you; anything else you must add yourself. Forgetting the mount is one of the most common
ways to break the API server: it exits at once with "no such file or directory".
</Callout>

## Using it

<Example title="See what kubectl really sends">
kubectl is only an HTTP client. Raise its verbosity to see the requests, or send one yourself.

```bash
kubectl get pods -n shop -v=6            # prints each URL and the response code
kubectl get --raw /api/v1/namespaces/shop/pods | head -c 300
kubectl get --raw '/readyz?verbose'      # the API server's own health checks, one per line
kubectl api-resources                    # every resource, its API group, short name and whether it is namespaced
kubectl auth whoami                      # the user and groups the API server sees you as
kubectl auth can-i create deployments -n shop --as jane
```

`/readyz?verbose` is worth remembering: a line such as `[-]etcd failed` tells you in one command that the API
server is up but cannot reach its database.
</Example>

<Example title="Change a flag safely on a kubeadm cluster">
Task: allow NodePorts from 30000 to 34000. Work on the control plane node, as root.

```bash
cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/kube-apiserver.yaml.bak   # outside the manifests folder
vi /etc/kubernetes/manifests/kube-apiserver.yaml
```

Add one line to the `command` list, with the same indentation as its neighbours:

```yaml
    - --service-node-port-range=30000-34000
```

Save. The kubelet notices the change within about half a minute, stops the old container and starts a new one. kubectl answers
"connection refused" in the meantime, so watch the runtime instead:

```bash
watch crictl ps --name kube-apiserver    # wait for a new container in state Running
kubectl -n kube-system get pod -l component=kube-apiserver
ps -ef | grep -o 'service-node-port-range=[^ ]*'
```
</Example>

<Example title="Fix an API server that will not start">
`kubectl get nodes` answers `The connection to the server 192.168.56.10:6443 was refused`. kubectl is useless now,
because the thing it talks to is the thing that is broken. Go to the control plane node and ask the container
runtime.

```bash
crictl ps -a --name kube-apiserver       # Exited, and the ATTEMPT number keeps growing
crictl logs <container-id> 2>&1 | tail   # the last lines name the cause
```

What the logs usually say, and what it means:

| The log says | Look at |
|--------------|---------|
| `unknown flag: --...` | A misspelt flag in the manifest |
| `dial tcp 127.0.0.1:2379: connect: connection refused` | Is etcd running? Is `--etcd-servers` right? |
| `open /etc/kubernetes/pki/...: no such file or directory` | A wrong path, or a file that is not mounted |
| `x509: certificate signed by unknown authority` | The wrong CA file in an `--etcd-cafile` or similar flag |

If `crictl ps -a` shows **no** kube-apiserver container at all, the kubelet could not even read the manifest:

```bash
journalctl -u kubelet --since "5 min ago" | grep -i -E "apiserver|manifest|yaml"
```

Fix the manifest (or restore your backup), then wait for the container and for `kubectl get nodes` to answer.
</Example>

## Tricks

<Trick title="Keep backups out of the manifests folder">
The kubelet runs **every** file in `/etc/kubernetes/manifests`, whatever its name. A copy called
`kube-apiserver.yaml.bak` in the same folder can be picked up as well, with confusing results. Copy
to `/root` or `/tmp` instead.
</Trick>

<Trick title="When kubectl is down, use crictl and the log files">
`crictl ps -a`, `crictl logs` and `journalctl -u kubelet` work without an API server. So do the log files the
runtime writes: `/var/log/pods/kube-system_kube-apiserver-*/kube-apiserver/*.log` and the links in
`/var/log/containers/`. If the container restarts too fast to catch, read the files.
</Trick>

<Trick title="Force a clean restart by moving the file">
To restart the API server, move the manifest out of the folder, wait until `crictl ps` no longer shows the
container, and move it back. The kubelet removes the Pod and creates it again from scratch.
</Trick>

<Trick title="Find a flag without scrolling">
`grep -n etcd /etc/kubernetes/manifests/kube-apiserver.yaml` is faster than paging through the file, and
`kubectl -n kube-system describe pod -l component=kube-apiserver` shows the same command when the server is up. To
compare with a healthy setup, the etcd manifest next to it shows the port etcd really listens on
(`--listen-client-urls`).
</Trick>

<Trick title="Tell 'not allowed' from 'not working'">
A 403 means the API server is healthy and said no. Use `kubectl auth can-i <verb> <resource> -n <namespace> --as
<user>` to confirm it, and fix RBAC rather than the server. For a ServiceAccount, the user name is
`system:serviceaccount:<namespace>:<name>`.
</Trick>

## Common mistakes

- **Editing the mirror Pod.** `kubectl edit pod kube-apiserver-cp1` cannot change the flags, and deleting the Pod
  does not restart the server. Only the file in `/etc/kubernetes/manifests` counts.
- **Breaking the YAML.** A tab, a wrong indent or a missing dash and the kubelet cannot read the manifest: the old
  container is stopped and no new one appears. The container logs are empty, so look in `journalctl -u kubelet`.
- **Not waiting.** After a change the API server needs up to a minute to come back, longer if the kubelet is backing
  off after several crashes. "Connection refused" for the first seconds is normal; check `crictl ps` before you
  change anything else.
- **Pointing at the wrong etcd port.** Clients use 2379. Port 2380 is for etcd members talking to each other.
- **Reading 401 and 403 as the same thing.** 401 means your credential was not accepted (an expired certificate,
  the wrong kubeconfig). 403 means you are known but not allowed.
- **Blaming the API server for everything.** If `kubectl get` works but new Pods stay `Pending`, the API server is
  fine: look at the scheduler. If Pods are scheduled but never start, look at the kubelet on that node.

## Recap

- The API server is the only door into the cluster and the only client of etcd; it is stateless.
- Every request goes through **authentication → authorization → admission** (mutating, schema check, validating)
  before it is stored. Reads skip admission.
- All other components work by **watching** the API server and writing results back to it.
- With kubeadm it is a **static Pod**: change it by editing `/etc/kubernetes/manifests/kube-apiserver.yaml`.
- When it is down, kubectl cannot help: use `crictl ps -a`, `crictl logs` and `journalctl -u kubelet`.
