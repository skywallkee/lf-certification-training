## Why dynamic provisioning exists

Without it, an administrator creates PersistentVolumes ahead of time and hopes their sizes match the
claims that arrive. Dynamic provisioning flips this: a claim names a class, and the class's provisioner
creates a volume that fits.

## Anatomy of a StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

- `provisioner` names the CSI driver that creates volumes.
- `parameters` are passed to that driver; their meaning is driver specific.
- `reclaimPolicy` applies to volumes this class creates: `Delete` (the default) or `Retain`.
- `volumeBindingMode: WaitForFirstConsumer` delays provisioning until a Pod uses the claim, so the
  volume is created in the Pod's zone.

## The default class

One class can carry the `is-default-class` annotation. With the DefaultStorageClass admission plugin
enabled, a claim that sets no `storageClassName` gets the default class written into it.

<Callout kind="warning" title="Empty string is not the same as unset">
`storageClassName: ""` asks for a volume with no class and skips dynamic provisioning entirely. Leaving
the field out asks for the default class.
</Callout>

## Requesting storage

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 10Gi
```

```bash
kubectl get storageclass
kubectl get pvc data -o wide
kubectl describe pvc data   # Events show provisioning progress or errors
```

## Expanding a volume

If the class sets `allowVolumeExpansion: true`, edit the claim's `spec.resources.requests.storage` to a
larger value. Shrinking is not supported.

## Common failures

| Symptom | Likely cause |
|---------|--------------|
| Claim Pending, no events | No default class and no `storageClassName` |
| Claim Pending with `WaitForFirstConsumer` | Normal until a Pod uses the claim |
| `ProvisioningFailed` event | Driver not installed or wrong parameters |

<Callout kind="tip" title="Exam habit">
Read the claim's events with `kubectl describe` before changing anything. They usually name the problem.
</Callout>

## Checklist

1. List classes and find the default.
2. Create the claim with the right class, size and access mode.
3. Mount it in a Pod and check the claim is `Bound`.
