## Why Services exist

A Deployment keeps your replicas running by replacing Pods: during every rollout, after every node failure, and
whenever a container is evicted. Each replacement Pod gets a **new IP address**. If clients talked to Pods directly
they would have to track those addresses, and they would also have to decide which replica to send each request to.

A **Service** solves both problems. It is a Kubernetes object that gives a group of Pods one DNS name and one
virtual IP address that stay the same for the Service's whole life, and it spreads connections across the Pods
that are ready to take them.

<KeyIdea>
A Service is a stable name and address in front of a changing set of Pods. Clients only ever talk to the Service;
Kubernetes keeps track of which Pods are behind it right now.
</KeyIdea>

## What a Service is made of

<Diagram id="service-routing" />

Four pieces work together:

- **The selector.** A Service has a label selector, such as `app: web`. Every Pod in the same namespace whose labels
  match is a candidate backend. The Service does not care which Deployment created the Pods; labels are the only link.
- **The EndpointSlice.** The EndpointSlice controller watches the Service and the Pods and writes the current list of
  matching Pod IPs and ports into EndpointSlice objects. Each address is marked ready or not ready, and only ready
  addresses receive traffic.
- **The virtual IP (ClusterIP).** When you create the Service, the API server gives it an IP from the cluster's
  service range, for example `10.96.0.20`. It never changes while the Service exists.
- **The DNS name.** Cluster DNS (CoreDNS) answers `web.shop.svc.cluster.local`, and the short forms `web` (from the
  same namespace) and `web.shop`, with that IP.

Ports are where most mistakes happen, so learn the three names once:

| Field | Meaning | Default |
|-------|---------|---------|
| `port` | The port clients call on the Service | required |
| `targetPort` | The port the container listens on (a number or the name of a container port) | same as `port` |
| `nodePort` | The port opened on every node (NodePort and LoadBalancer only) | a free port from 30000 to 32767 |

## How traffic really reaches a Pod

<Diagram id="kube-proxy" />

The ClusterIP is **virtual**: no network interface has it and no process listens on it. That surprises most people
the first time they try to `ping` a Service and get no answer.

What makes it work is **kube-proxy**, which runs on every node. It watches the API server for Services and
EndpointSlices and programs the node's kernel, with iptables or nftables rules (or IPVS). When a Pod sends a packet
to `10.96.0.20:80`, the kernel **on the sending Pod's node** matches the rule, picks one ready backend and rewrites
the packet's destination to that Pod's real address, for example `10.244.2.4:8080`. Replies are translated back on
the way out, so the client never sees the Pod address.

<DeepDive title="What happens to each connection">
- The choice of backend is made **per connection**, not per request. A client that keeps one connection open (HTTP
  keep-alive, gRPC) keeps talking to the same Pod. That is why a Deployment can look unbalanced under gRPC.
- In iptables mode the backend is picked at random; IPVS mode supports round robin and other schedulers.
- `sessionAffinity: ClientIP` sends all connections from one client IP to the same Pod, for a while (three hours by
  default).
- Because the rewrite happens in the kernel of the client's node, kube-proxy can be restarted without breaking
  traffic: the rules stay in place until it writes new ones.
- A **headless Service** (`clusterIP: None`) gets no virtual IP and no kube-proxy rules at all. DNS then answers with
  the ready Pods' IPs directly, which is what StatefulSets use to give each Pod its own name.
</DeepDive>

## The four types

<Diagram id="service-types" />

| Type | Reachable from | What Kubernetes adds |
|------|----------------|----------------------|
| `ClusterIP` (default) | Inside the cluster | A virtual IP and a DNS name |
| `NodePort` | Anything that can reach a node | ClusterIP, plus the same port opened on every node |
| `LoadBalancer` | Outside, through the cloud | NodePort, plus a load balancer from the cloud provider |
| `ExternalName` | Inside the cluster | Only a DNS CNAME to another name; no proxying at all |

The first three stack: a LoadBalancer Service also has a node port and a cluster IP, and you can use any of them.
On a cluster without a cloud provider (kubeadm on bare VMs, kind, k3s) a LoadBalancer Service waits with its
`EXTERNAL-IP` showing `<pending>` unless something like MetalLB, or k3s's built-in ServiceLB, hands out addresses.

<Callout kind="warning" title="NodePort is not a firewall rule">
A node port is open on **every** node, including nodes that run none of the Pods: the node forwards the connection
to a Pod elsewhere. Set `externalTrafficPolicy: Local` to answer only on nodes with a local Pod and keep the client's
source IP.
</Callout>

## Using it

<Example title="Expose a Deployment and prove it works">
The Deployment `web` in namespace `shop` runs Pods labelled `app: web` that listen on port 8080. Expose it inside the
cluster on port 80, then check every link in the chain.

```bash
kubectl -n shop expose deployment web --port=80 --target-port=8080
kubectl -n shop get svc web                      # has a CLUSTER-IP
kubectl -n shop get endpointslices -l kubernetes.io/service-name=web   # lists Pod IPs
kubectl -n shop run tmp --rm -it --restart=Never --image=busybox:1.37 -- wget -qO- http://web
```

`kubectl expose` copies the Deployment's selector into the Service, so the selector cannot be wrong. Add
`--type=NodePort` to open a node port as well.
</Example>

<Example title="Write the manifest when you need a fixed node port">
`kubectl expose` cannot set `nodePort`. Generate the manifest, add the field, then apply it:

```bash
kubectl -n shop expose deployment web --port=80 --target-port=8080 --type=NodePort \
  --dry-run=client -o yaml > web-svc.yaml
```

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: shop
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
```
</Example>

## Tricks

<Trick title="Let kubectl write the YAML">
`--dry-run=client -o yaml` turns any `kubectl create` or `kubectl expose` command into a manifest you can edit. It is
faster and safer than typing a Service from memory, and the selector and ports come out right.
</Trick>

<Trick title="Debug from the endpoints inward">
When a Service does not answer, run `kubectl get endpointslices -l kubernetes.io/service-name=<name>` first.
**No addresses** means the selector matches no ready Pod: compare `kubectl get svc <name> -o wide` (the SELECTOR
column) with `kubectl get pods --show-labels`. **Addresses but no answer** means the `targetPort` is wrong or the
app listens on another port.
</Trick>

<Trick title="Use the full name across namespaces">
From another namespace, the short name does not resolve. Use `web.shop` or `web.shop.svc.cluster.local`.
</Trick>

## Common mistakes

- **Selector typos.** `app: Web` and `app: web` are different labels. The Service is created without complaint and
  simply has no endpoints.
- **Port confusion.** Clients call `port`; the container listens on `targetPort`. Swapping them is the most common
  reason a Service has endpoints but connections are refused.
- **Pods that are not ready.** A Pod that fails its readiness probe is removed from the endpoints, so a broken probe
  looks exactly like a broken selector. Check `kubectl get pods`: the READY column shows it.
- **Pinging the Service.** ICMP to a ClusterIP usually gets no reply, because only the Service's ports have rules.
  Test with the real protocol (`wget`, `curl`, `nc`).

## Recap

- A Service gives changing Pods one stable DNS name and virtual IP.
- Its **selector** decides which Pods; the **EndpointSlice** lists the ready ones.
- **kube-proxy** writes kernel rules on every node; the kernel forwards each connection to a Pod.
- `ClusterIP` → `NodePort` → `LoadBalancer` each add a way in; `ExternalName` is only a DNS alias.
- In the exam: `kubectl expose`, `--dry-run=client -o yaml`, and check the endpoints first when something fails.
